# 数据源模块概览

## 1. 模块职责

数据源模块主要解决四个问题：

1. 保存外部数据源连接配置。
2. 校验当前配置是否能够连通目标数据源。
3. 抽取目标数据源中的表、列、主键和外键信息。
4. 将这些元数据缓存到 Seedar 自身元数据库中，供后续语义建模与查询使用。

从系统设计角度看，它既是“连接管理模块”，也是“元数据入口模块”。

## 2. 为什么这个模块重要

系统后续的 `dataset`、`query`、`ai chart-recommend` 等模块并不直接面对真实数据库 schema，而是依赖这个模块产出的元数据缓存。

因此它的重要性体现在：

- 它决定后续建模是否有足够上下文。
- 它决定表结构、字段类型和外键关系是否被正确识别。
- 它影响后续自动 Join、字段锁定和图表推荐等能力的准确性。

## 3. 入口划分

### 3.1 前端入口

- 列表页 `/datasource`
- 详情页 `/datasource/:id`

前端关注的是：

- 数据源卡片列表
- 创建与删除弹窗
- 数据源详情中的表结构与关系信息

### 3.2 后端入口

后端核心入口为：

- `DatasourceController`
- `DatasourceService`

其中：

- Controller 负责 HTTP 资源编排
- Service 负责连接测试、元数据抓取、加解密和缓存写入

### 3.3 元数据实体

围绕数据源形成的核心实体包括：

- `Datasource`
- `DatasourceTable`
- `DatasourceColumn`
- `DatasourceForeignKey`
- `DatasourceMetaVersion`

## 4. 模块边界

### 4.1 它负责什么

- 数据源连接定义
- 配置校验
- 连接测试
- 元数据抓取
- 元数据缓存

### 4.2 它不负责什么

- 数据集字段语义定义
- 指标定义
- 查询执行
- 图表渲染

这些职责分别落在：

- `dataset`
- `query`
- `dashboard`

## 5. 上下游关系

### 5.1 上游

上游只有一个直接来源：

- 用户通过前端表单输入连接信息

### 5.2 下游

该模块的结果会被以下模块消费：

- `dataset`：读取可选表、列、外键，构建语义模型
- `query`：间接依赖字段类型与关系信息
- `ai`：读取数据集、字段等上下文后为用户提供查询和图表推荐

## 6. 关键实现特征

### 6.1 连接配置与数据库类型分离

数据源使用：

- `type`
- `config`

组合表示真实连接。

这是一种典型的“多类型资源统一建模”方式，方便后续扩展更多数据源。

### 6.2 敏感信息加密

配置在保存前会进行加密，在读取时再解密。

这意味着系统明确意识到数据源配置属于敏感资产，而不是普通业务字段。

### 6.3 元数据缓存而非实时扫描

系统没有在每次前端打开页面时重新扫描目标数据库，而是将表、列和外键缓存到自身数据库中。

这种设计的好处是：

1. 读取更快。
2. 下游模块可以用统一结构消费元数据。
3. 数据集建模时无需频繁直连真实数据库查询 schema。

### 6.4 对不同数据库采用差异化 schema 抓取逻辑

从 `DatasourceService` 可见，MySQL、PostgreSQL、ClickHouse 会走不同的元数据抓取逻辑。

这说明该模块不是简单“连通即可”，而是承担了跨数据库方言适配责任。

## 7. 论文可用描述

如果需要在论文中描述数据接入模块，可以这样概括：

“数据源模块是系统的统一接入层，负责对外部异构数据库进行连接管理、可用性验证与元数据抽取，并将表结构、字段类型与外键信息缓存到平台元数据库中，为后续语义建模、查询执行与智能推荐提供统一的数据基础。”
