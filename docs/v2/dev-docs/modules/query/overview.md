# 查询模块概览

## 1. 模块职责

查询模块负责：

- 保存 Query 资产
- 接收临时 DSL 预览请求
- 把 DSL 转成 QuerySpec
- 调用 `metric_engine` 生成 SQL
- 在真实数据源上执行 SQL
- 把结果、SQL、列映射回传给前端

换句话说，它承担了“从用户分析意图到最终结果集”的完整执行闭环。

## 2. 设计动机

Seedar 没有让前端直接提交 SQL，而是设计了 DSL + 引擎式执行链，背后的原因主要有：

1. 前端不需要理解数据库方言。
2. Query 能以更高层语义保存和复用。
3. Join、字段映射、指标表达可以由后端统一控制。
4. 便于后续接入 AI、图表推荐与结构化解释能力。

## 3. 上下游关系

### 3.1 上游

查询模块的直接上游主要是：

- `dataset`
- `panel`
- 前端查询编辑器

其中 `dataset` 提供语义模型，`panel` 提供使用场景，而前端编辑器负责产生 DSL。

### 3.2 下游

查询模块的直接下游包括：

- 真实外部数据库
- `metric_engine`

它既依赖外部数据源拿结果，也依赖引擎层生成正确 SQL。

## 4. 为什么它是系统中枢

因为它同时理解四种完全不同的语义：

1. 业务语义层：字段、指标、数据集
2. 查询表达层：DSL
3. 执行层：QuerySpec 与 SQL
4. 展示层：列映射、结果头与面板消费格式

在整个系统中，没有其他模块同时承担这四层转换责任。

## 5. 模块内部的关键子问题

从实现角度看，本模块至少包含以下子问题：

### 5.1 Query 资产管理

系统不仅要“查一次”，还要保存：

- Query 名称
- Query 所属数据集
- Query DSL
- Query 状态

### 5.2 临时查询执行

用户在面板编辑页运行预览时，不一定已经持久化 Query，因此系统必须支持临时执行。

### 5.3 动态 Join 推导

当前实现取消了前端显式传 joins，由后端根据 DSL 依赖字段自动推导查询所需 Join 路径。

### 5.4 指标表达解析

系统不仅支持简单聚合指标，还支持：

- 行级指标
- 算术指标
- 后聚合指标
- 周期对比指标

### 5.5 结果映射

系统返回的不只是结果行，还包括 SQL、执行时间与列映射，这对前端显示和调试非常重要。

## 6. 关键实现特征

### 6.1 DSL 与 SQL 解耦

系统通过：

`QueryDSL -> QuerySpec -> SQL`

实现前端表达和数据库执行之间的解耦。

### 6.2 引擎独立成包

`metric_engine` 被独立到 `packages/metric_engine`，说明项目明确希望把查询与表达式能力当成平台级基础设施，而不是临时业务代码。

### 6.3 结果结构偏展示友好

最终返回结构已经考虑到了：

- 表头
- 数据行
- 业务列名映射
- 执行耗时

这说明查询模块并不只服务后端，而是直接面向前端消费体验。

## 7. 论文可用描述

如果需要在论文中概括查询模块，可以写成：

“查询模块是系统的核心执行中枢，它一方面承接来自语义数据集的数据模型与前端 DSL 配置，另一方面通过指标引擎完成 Join 推导、表达式解析与 SQL 生成，并最终在外部数据源上执行查询，将结果以适合前端展示和调试的结构返回，从而形成从语义查询到可视化结果的闭环。”
