# 数据集模块概览

## 1. 模块职责

数据集模块的职责是把数据源层的物理结构提升为可分析的语义结构。

更具体地说，它负责五类事情：

1. 选择哪些源表被纳入当前数据集。
2. 定义哪些字段被暴露给查询层。
3. 约束主键与表关系，保证模型基本正确性。
4. 管理多表 Join 关系。
5. 定义指标体系，支撑后续 DSL 查询与图表配置。

从产品角度看，数据集是系统中的“分析语义载体”；从技术角度看，它是 `datasource` 与 `query` 之间的中间抽象层。

## 2. 设计动机

为什么系统不直接让用户对源表写查询，而是要先建数据集？

原因至少有四个：

1. 源表字段名往往偏技术化，不适合直接暴露给业务用户。
2. 多表关系与主键规则需要被显式组织。
3. 指标定义需要长期复用，不能每次临时拼装。
4. AI 与图表推荐需要稳定的语义上下文，而不是临时 SQL。

因此，数据集层实际上承担了“从数据库结构到业务分析结构”的转换。

## 3. 模块边界

### 3.1 向上承接

它向上承接：

- 数据源元数据
- 表结构
- 列信息
- 外键关系

这些信息来自 `datasource` 模块。

### 3.2 向下输出

它向下输出：

- Query 可执行所需的表语义结构
- 字段及业务名
- 指标定义
- Join 配置

这些结果被 `query`、`dashboard` 和 `ai` 模块间接消费。

## 4. 核心约束

数据集模块并不是任意保存前端表单，而是存在明确建模约束：

1. 数据集必须挂在一个数据源下面。
2. 字段不能为空。
3. 如果某个表有主键，则主键字段必须被纳入数据集。
4. 多表建模时必须存在可用 Join。
5. 删除数据集前必须确认没有 Query 依赖它。

这些规则说明，系统并不把数据集视为“随便配配置”，而是视为可被后续模块依赖的核心资产。

## 5. 核心子对象

### 5.1 `Dataset`

表示一个完整语义数据集，是所有下级建模对象的根。

### 5.2 `DatasetTable`

描述该数据集由哪些源表构成，以及主表是谁。

### 5.3 `DatasetField`

描述用户在数据集中实际暴露哪些字段，以及这些字段的：

- 名称
- 类型
- 描述
- 业务名
- 是否主键

### 5.4 `DatasetJoin`

描述多表数据集中的关联结构，是后续动态 Join 推导的基础之一。

### 5.5 `DatasetMetric`

描述数据集级别的指标定义，是系统分析能力的关键组成部分。

## 6. 前端设计特征

前端数据集编辑不是单页直接提交，而是多步骤编辑器：

- 基本信息
- 数据源与表选择
- Join 配置
- 字段选择
- 指标配置
- 确认提交

这种设计有两个意义：

1. 降低复杂建模的认知负担。
2. 让后端最终接收到的是一份结构完整的建模请求，而不是碎片化更新。

## 7. 后端设计特征

后端 `DatasetService` 的设计特征比较明显：

1. 强调事务处理。
2. 强调建模校验。
3. 把字段、指标、Join、表的处理拆成辅助 manager。
4. 查询时会尽量批量读取，减少 N+1 风险。

这说明数据集模块不只是“表单落库”，而是具备较强的模型一致性设计意识。

## 8. 论文可用描述

如果在论文中描述数据集模块，可以概括为：

“数据集模块位于数据源接入与查询执行之间，负责将原始数据库表结构抽象为可面向分析场景复用的语义模型。该模块通过字段、主键、连接关系与指标定义，将技术层数据结构转换为业务分析层数据结构，为查询 DSL、图表构建与 AI 辅助推荐提供统一语义基础。”
