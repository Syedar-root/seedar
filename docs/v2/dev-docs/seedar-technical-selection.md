# Seedar 技术选型分析

## 1. 文档目的

本文总结 Seedar 的核心技术栈、选型原因、实际收益与潜在代价。

对于毕业论文，这篇文档适合作为“技术路线与方案论证”材料。

## 2. 前端技术栈

### 2.1 React 18

用途：

- 构建组件化前端界面
- 承载复杂交互式页面，如数据集编辑器、面板编辑器与 AI 侧栏

选型原因：

1. 组件生态成熟
2. 与可视化、拖拽、状态管理生态兼容性好
3. 适合构建高交互管理后台与可视化工作台

代价：

- 状态层需要额外设计，否则容易出现复杂的跨组件状态耦合

### 2.2 Vite

用途：

- 前端开发与构建工具

选型原因：

1. 启动快、热更新快
2. 配置相对轻量
3. 对 TypeScript 与现代前端生态支持较好

### 2.3 React Router

用途：

- 页面路由管理

适用性：

- Seedar 是典型的多页面工作台系统，业务切片清晰，适合使用前端路由进行模块组织

### 2.4 React Query

用途：

- 管理服务端数据状态
- 提供缓存、失效重取、异步状态管理

选型原因：

1. 数据源、数据集、查询、仪表盘等都天然适合请求缓存模型
2. 可以将远端数据状态和本地 UI 状态分开

### 2.5 Zustand

用途：

- 管理局部或全局本地状态

适用场景：

- AI 侧栏开关
- workflow action 队列
- AI 场景状态

选型原因：

1. 轻量
2. 学习成本低
3. 适合中等规模全局状态，不必引入更重的状态方案

## 3. 前端展示与交互相关技术

### 3.1 react-dnd

用途：

- 面板编辑、字段拖拽等交互

### 3.2 react-resizable-panels

用途：

- 左右分栏布局与 AI 侧栏伸缩

### 3.3 @visactor/react-vchart 与 @visactor/react-vtable

用途：

- 图表渲染
- 表格渲染

选型原因：

1. 能覆盖图表、表格等典型数据展示场景
2. 适合和自定义 Query 结果渲染链结合

## 4. 后端技术栈

### 4.1 NestJS

用途：

- 构建后端 API 服务与模块化业务系统

选型原因：

1. 模块化组织清晰
2. 适合控制器、服务、实体、DTO 分层
3. 对于毕业论文中的“后端模块设计”表达非常友好

### 4.2 TypeORM

用途：

- 管理 Seedar 自身元数据库

选型原因：

1. 适合管理 DataSource、Dataset、Query、Panel、Dashboard 等平台元数据
2. 与 NestJS 集成成熟
3. 支持 migration，便于数据库版本演进

### 4.3 Knex

用途：

- 连接并执行外部业务数据源查询

选型原因：

1. 更适合作为跨数据库查询执行层
2. 与自研 `metric_engine` 的 SQL 生成链更契合

### 4.4 class-validator / class-transformer

用途：

- DTO 校验与对象转换

价值：

- 保证接口输入具备基础结构约束

## 5. 查询与指标引擎相关技术

### 5.1 自研 `@metric-engine/core`

用途：

- 表达式系统
- QuerySpec
- SQL 构建
- 兼容层

为什么不用纯 ORM 查询：

1. ORM 不适合表达复杂的指标和派生维度
2. Query DSL 与 SQL 生成需要独立抽象层
3. 不同数据库方言下需要更强控制力

### 5.2 jsep

用途：

- 表达式解析

价值：

- 支撑表达式型指标与表达式维度

## 6. AI 技术栈

### 6.1 LangChain

用途：

- 模型抽象
- 工具调用
- prompt 与 agent 编排

选型原因：

1. 便于统一接入 OpenAI、Anthropic、DeepSeek
2. 工具体系成熟
3. 适合和自定义 ToolService 配合

### 6.2 LangGraph

用途：

- 图式 agent 流程编排
- interrupt / resume

价值：

- 适合构建“clarify -> act”两阶段对话流程
- 适合实现 workflow 中断与恢复

### 6.3 DeepAgents

用途：

- 深层 agent 与技能目录机制

价值：

- 让 AI 能力通过 skill 文件逐步扩展，而不是全部写死在一个 prompt 中

## 7. 部署与运维技术栈

### 7.1 Docker / Docker Compose

用途：

- 运行时编排
- 标准化部署

选型原因：

1. 降低部署差异
2. 前后端与数据库可统一打包
3. 便于 CLI 管理

### 7.2 自研 CLI

用途：

- 安装、升级、状态、日志、诊断

价值：

- 把部署知识从“阅读仓库脚本”转为“可执行命令”

## 8. 选型背后的整体原则

从整体看，Seedar 的技术选型体现了四个原则：

### 8.1 分层清晰

- React 页面层
- 共享 hooks / API 层
- NestJS 业务层
- Query 引擎层
- AI 编排层

### 8.2 契约优先

通过 `packages/types` 让前后端共享类型定义。

### 8.3 查询能力独立

把查询与 SQL 生成从业务模块中抽离成独立引擎。

### 8.4 运维可交付

通过 CLI + Docker 的组合，使系统具备可部署、可升级、可诊断的工程能力。

## 9. 可在论文中采用的总结表述

可以将 Seedar 的技术路线概括为：

“系统前端采用 React + Vite + React Query + Zustand 构建交互式分析工作台，后端采用 NestJS + TypeORM 实现模块化服务架构，并结合 Knex 与自研指标引擎完成跨数据源查询执行。同时，系统引入 LangChain、LangGraph 与 DeepAgents 构建具备工具调用和 workflow 能力的智能辅助模块，最终通过 Docker 与 CLI 实现标准化部署和运维。”
