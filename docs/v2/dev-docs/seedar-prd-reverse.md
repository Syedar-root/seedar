# Seedar 产品需求反推文档

## 1. 文档定位

本文不是传统意义上由产品经理编写的正式 PRD，而是基于当前代码实现、页面结构、接口设计和部署方式，对 Seedar 产品目标、用户角色、核心流程、边界范围与非功能特征进行逆向整理。

这份文档适合承担三类用途：

1. 作为毕业论文中“需求分析”“系统目标”“研究意义”的一手素材。
2. 作为项目总览材料，帮助新接手成员从“为什么做”而不是“目录长什么样”开始理解系统。
3. 作为后续真正补写正式 PRD 或需求规格说明书的基础草稿。

## 2. 反推方法说明

本次反推主要依据以下信息来源：

- 前端路由、页面结构与交互流程
- 后端核心模块、实体、DTO 与 service 逻辑
- 数据库迁移与实体模型
- AI 与 workflow 相关代码
- CLI 与部署配置

因此，本文中的结论可以分为两类：

- `可直接确认`：能够从代码中明确验证。
- `推断`：高度符合实现意图，但仍建议结合实际产品计划再次确认。

## 3. 产品一句话定义

Seedar 可以被定义为：

“一个面向数据分析场景的、集数据源接入、语义数据集建模、DSL 查询执行、可视化面板编排、仪表盘展示与 AI 辅助 workflow 于一体的全栈分析平台。”

这一定义比“图表系统”更准确，也比“聊天助手”更贴近真实实现。

## 4. 产品要解决的核心问题

从现有实现反推，Seedar 主要试图解决以下五类问题：

### 4.1 外部数据源接入成本高

在传统场景下，业务人员即使已经拥有数据库，也很难快速把这些数据变成可持续分析的资产。原因包括：

- 不同数据库类型接入成本不同
- 表结构复杂，难以直接理解
- 外键信息与字段语义通常没有被很好组织

Seedar 的解决方式是提供“数据源 + 元数据抓取 + 元数据缓存”的统一接入层。

### 4.2 业务分析依赖手写 SQL

很多系统只能在“给定 SQL”之后才能展示图表，这会带来两个限制：

1. 业务用户不会写 SQL。
2. SQL 本身难以沉淀成更高层的资产。

Seedar 的解决方式是引入：

- 语义数据集
- Query DSL
- 指标定义体系

从而把“分析表达”从 SQL 层抬升到语义层。

### 4.3 分析资产难以复用

传统分析流程里，图表、查询、看板经常是一次性产物。Seedar 明显希望解决这一问题，因为其设计中存在完整的资产层：

- 数据源资产
- 数据集资产
- 查询资产
- 面板资产
- 仪表盘资产

这说明产品目标不是临时查一次，而是沉淀长期可复用的分析对象。

### 4.4 页面操作复杂，搭建门槛高

即使系统支持拖拽和配置，用户在多步骤搭建数据集、查询和图表时仍会遇到：

- 不知道该选哪个字段
- 不知道该配置什么图表
- 不知道该如何修正配置

Seedar 的回应是加入 AI 辅助模块，并且这个 AI 不是单纯聊天，而是能感知页面上下文、调用工具、执行 workflow。

### 4.5 部署与交付复杂

如果一个平台只能通过源码和脚本部署，它很难真正进入交付阶段。Seedar 明确引入 CLI 作为安装与升级入口，说明产品目标不只是“内部原型”，而是逐步朝“可部署、可交付、可维护的系统”演进。

## 5. 目标用户分析

## 5.1 主要用户

根据页面结构与功能重心，当前最可能的主要用户是：

### 1. 数据分析师 / BI 使用者

他们的关注点通常是：

- 能否接入数据
- 能否快速建模
- 能否复用查询与图表
- 能否形成可演示的看板

Seedar 的数据源、数据集、面板和仪表盘链路与这一角色高度吻合。

### 2. 数据产品或业务分析平台建设者

这类用户不仅关心展示，还关心：

- 数据语义层建设
- 查询能力抽象
- 可视化资产沉淀
- 系统部署与运维

Seedar 的 monorepo、CLI 与查询引擎设计，明显也服务这一类用户。

## 5.2 次级用户

### 1. 前后端开发者

他们通常负责：

- 扩展数据源类型
- 增加图表组件
- 调整 DSL 或指标体系
- 接入更多 AI 能力

### 2. 运维或交付人员

他们的关注点是：

- 安装
- 升级
- 日志
- 健康检查
- 版本管理

CLI 的存在使这一角色成为真实用户，而不是附属角色。

## 5.3 当前尚不明显的用户角色

从当前实现看，以下角色并不突出：

- 多租户组织管理员
- 权限管理员
- 面向公开终端的普通访客

因此可以推断，当前系统更多还是面向内部分析平台或受控使用环境。

## 6. 产品目标拆解

## 6.1 总体目标

构建一个支持“从数据接入到分析交付”的闭环系统。

## 6.2 分阶段目标

从实现层次看，产品目标可拆成以下阶段：

### 阶段一：接入层

目标：

- 让用户接入数据库并获取元数据

对应能力：

- 数据源管理
- 连接测试
- 表结构抓取
- 外键抓取

### 阶段二：语义建模层

目标：

- 让用户从物理表构造业务友好的数据集

对应能力：

- 选表
- 字段配置
- Join 配置
- 指标定义

### 阶段三：查询表达层

目标：

- 让用户无需写 SQL，也能表达分析需求

对应能力：

- Query DSL
- 临时查询
- 查询资产化

### 阶段四：展示交付层

目标：

- 让查询结果变成可复用的面板与可交付的仪表盘

对应能力：

- Panel
- Dashboard
- 布局编辑

### 阶段五：智能辅助层

目标：

- 降低复杂配置的认知门槛

对应能力：

- AI 对话
- 字段业务名生成
- 数据查询 skill
- 图表推荐 skill
- workflow interrupt

### 阶段六：交付运维层

目标：

- 让系统具备实际部署和升级能力

对应能力：

- CLI 安装
- CLI 升级
- 日志与诊断
- Docker 运行时模板

## 7. 核心业务场景

## 7.1 场景一：接入业务数据库

### 用户诉求

- 输入数据库连接信息
- 验证连接是否可用
- 看到这个库中有哪些表、字段、外键

### 系统响应

- 创建数据源对象
- 测试连接
- 将表结构与关系缓存进元数据库

### 业务价值

- 用户不再面对一片未知数据库，而是得到可理解的元数据入口

## 7.2 场景二：构建业务数据集

### 用户诉求

- 从源表中挑出分析所需部分
- 给字段配置更业务化的名称
- 配置主键与表关联
- 定义指标

### 系统响应

- 构建 `dataset`
- 保存 `dataset_field`
- 保存 `dataset_join`
- 保存 `dataset_metric`

### 业务价值

- 把技术结构转成业务语义结构

## 7.3 场景三：在面板页构造查询

### 用户诉求

- 拖入维度、指标和过滤条件
- 立即查看结果
- 决定是否保存为面板

### 系统响应

- 组装 DSL
- 执行临时查询
- 预览 SQL 与结果

### 业务价值

- 提供低门槛分析试验场

## 7.4 场景四：配置图表与指标卡

### 用户诉求

- 选择适合的图表展示方式
- 调整配置
- 保存展示资产

### 系统响应

- 保存 `panel`
- 绑定查询与可视化配置

### 业务价值

- 从“数据结果”进一步沉淀为“展示资产”

## 7.5 场景五：编排仪表盘

### 用户诉求

- 将多个面板组合为一个工作台
- 调整布局
- 切换浏览和编辑模式

### 系统响应

- 保存 `dashboard`
- 保存 `dashboard_panels`
- 保存 `layout`

### 业务价值

- 将零散分析结果整合成面向使用者的交付物

## 7.6 场景六：使用 AI 协助搭建

### 用户诉求

- 在当前页面中直接提问
- 获得图表推荐
- 获得数据查询帮助
- 通过 workflow 快速完成某些操作

### 系统响应

- 创建或复用 AI 会话
- 流式返回消息
- 必要时触发前端动作工作流

### 业务价值

- 降低新用户上手门槛，提升复杂操作效率

## 8. 已实现范围

从当前代码可以明确确认，系统已经实现了以下范围：

### 数据接入侧

- 数据源列表、详情、创建、更新、删除
- 连接测试
- 元数据抓取与缓存

### 建模侧

- 数据集创建、编辑、详情、删除
- 多步骤建模流程
- 字段、Join、指标配置

### 查询侧

- Query 创建、更新、删除
- 临时查询执行
- SQL 生成与结果回传

### 展示侧

- 面板列表与编辑
- 面板状态切换
- 仪表盘查看与编辑
- 布局更新

### AI 侧

- AI 模型配置管理
- AI 会话
- 流式聊天
- 字段业务名生成
- workflow interrupt

### 运维侧

- 安装 CLI
- 启停、升级、日志、状态、诊断

## 9. 暂未充分体现或尚需确认的需求

以下内容当前要么尚不明显，要么还处于“代码侧有基础，但产品边界未完全清晰”的状态：

### 9.1 权限与角色体系

当前并未看到特别完整的：

- 用户认证
- 角色权限
- 数据隔离

因此推断：

- 当前系统仍偏单租户或受控内部环境

### 9.2 协作能力

当前没有明显的：

- 评论
- 共享链接策略
- 审批流
- 多人协作编辑

### 9.3 更丰富的数据源生态

代码层面已经支持：

- MySQL
- PostgreSQL
- ClickHouse
- CSV
- Excel 类型结构

但从完整流程看，文件型数据源是否已经具备与数据库型同等成熟度，还需要继续确认。

### 9.4 更高级的 AI 自动化能力

当前 AI 已经能：

- 读取数据集
- 执行临时查询
- 推荐图表
- 触发 workflow

但是否会进一步扩展到：

- 自动建数据集
- 自动建面板
- 自动排查错误

仍然属于后续可能演进方向。

## 10. 非功能需求反推

除了显性功能需求，现有实现中还隐含了多项非功能需求。

### 10.1 可维护性

证据：

- monorepo 分层
- 共享类型包
- 业务模块分层
- 查询引擎独立成包

说明系统明确希望支持持续演进。

### 10.2 可扩展性

证据：

- 数据源类型使用 `type + config` 模式
- 指标类型使用枚举与多字段组合
- AI skill 与 tool 机制

说明系统被设计成可扩展平台，而不是一次性原型。

### 10.3 可部署性

证据：

- CLI
- Docker 模板
- release 流程

说明系统不仅追求可运行，也追求可交付。

### 10.4 可观察性

证据：

- 全局日志
- doctor/status/logs 命令
- 升级与安装状态文件

说明系统已开始考虑诊断与运维。

## 11. 产品边界总结

## 11.1 当前明确覆盖

- 数据分析平台内部工作流
- 语义建模与查询配置
- 看板构建与可视化输出
- AI 辅助式操作
- Docker 化交付

## 11.2 当前尚未明显覆盖

- 企业级权限与组织体系
- 面向公网的大规模用户系统
- 强协作型产品能力
- 完整审计和审批流程

## 12. 论文可直接使用的表述

### 12.1 系统目标表述

“本系统旨在面向数据分析与可视化场景，构建一套集数据源接入、语义数据集建模、查询表达、图表配置、仪表盘展示与智能辅助于一体的分析平台，从而降低业务用户获取分析结果的门槛，提高分析资产的复用能力与系统交付效率。”

### 12.2 研究意义表述

“与传统依赖手写 SQL 和一次性图表配置的分析方式不同，本系统通过语义建模与 DSL 查询机制提升了分析表达抽象层次，并通过 AI 与 workflow 机制增强了复杂操作过程中的辅助能力，对内部分析平台的低门槛化与工程化具有一定研究与实践意义。”

## 13. 一句话结论

如果要从产品视角给 Seedar 做一个准确定位，它更像是：

“一个带有 AI 辅助能力的数据建模与分析工作台”，而不是单纯的图表展示系统、查询工具或聊天机器人。
