# Seedar FAQ

## 1. 为什么前端拿到的不是完整 HTTP 响应，而是业务对象？

因为后端会把成功响应统一包装成：

```ts
{ success, code, message, data }
```

而前端 `ApiClient` 默认开启 `autoParseResponse`，会直接返回 `data` 字段。

如果你在浏览器里看到后端响应结构和前端拿到的不一样，这是正常现象。

## 2. 为什么创建数据源成功了，但详情页没有完整表结构？

可能原因：

- 创建时连接能通，但抓取元数据失败
- 外键读取失败
- 元数据缓存未完整刷新

代码上，数据源创建和元数据抓取并不是完全同一失败语义。也就是说，数据源记录可能已存在，但表/列/外键信息不完整。

建议排查：

1. 看后端日志是否有 `SaveTablesAndColumns` 或 `SaveForeignKeys` 相关错误。
2. 重新执行一次数据源更新，观察元数据是否被刷新。
3. 检查真实数据库用户是否有读取 schema 的权限。

## 3. 为什么创建多表数据集时报关联关系错误？

当前规则是：

- 如果请求里显式传了 `joins`，后端按显式关系保存。
- 如果没传 `joins`，后端会尝试从数据源外键关系自动推导。
- 如果两者都没有，就会拒绝创建。

所以当源库本身没有外键，或者外键没被成功抓取时，多表建模必须手动补足 join 定义。

## 4. 为什么删除数据集会失败？

常见原因：

- 该数据集已经被 Query 引用

后端会在删除前查询依赖它的 Query，并返回阻断错误。这是为了防止面板和仪表盘链路被静默破坏。

## 5. 为什么删除面板后，查询也没了？

这是当前后端实现的既定行为。

`PanelService.remove()` 在事务中删除面板后，会继续删除该面板关联的 Query。当前实现默认把 Query 视为面板私有资产。

风险：

- 如果未来一个 Query 会被多个面板复用，这个策略需要重新设计。

## 6. 为什么前端默认请求 `/api`，但本地调试时会 404？

因为前端默认 API 基址是：

```text
/api
```

这依赖于：

- Vite dev server 已经配置代理
- 或者你通过反向代理转发到 Nest 服务

如果没有代理，就需要显式设置 `VITE_API_BASE_URL`。

## 7. 为什么数据源更新后还会重新抓表结构？

因为后端把“连接配置变化”视为元数据可能变化的信号。

即使只是改了库地址或账号，表结构、权限、外键都可能发生变化，所以会重新抽取表、列、外键信息。

## 8. 为什么 AI 面板看起来像聊天，但行为又像操作系统？

因为它不只是文本对话组件。

当前 AI 侧栏还具备：

- 页面场景感知
- workflow interrupt
- 前端动作分发
- 会话恢复

也就是说，它既是聊天 UI，也是前端动作编排入口。

## 9. workflow 卡住时先看哪里？

优先检查以下几层：

1. AI SSE 是否已经收到 interrupt。
2. `useWorkflowInterruptExecutor` 是否识别到该 interrupt。
3. `WorkflowActionsStore` 中是否生成了 pending/running action。
4. 对应页面或组件是否真的消费了该 action。
5. 是否触发了超时，导致 action 被标记为 failed。

## 10. 为什么 `UserPage` 看起来不像真正的用户管理？

因为当前实现里它直接渲染了一个固定 `dashboardId` 的 `SeedarDashboard`。从代码看，它更像演示或试验性页面，而不是成熟的用户域。

## 11. `pnpm dev` 为什么不推荐当日常启动命令？

因为根脚本会递归并行执行各 workspace 的 `start:dev`，在当前 monorepo 里容易把不需要的包一起带起来，增加噪音和排查成本。

更建议分别启动：

- `pnpm dev:server`
- `pnpm dev:web`

## 12. 本地最容易忽略的配置是什么？

最常见的是这三类：

1. 后端数据库连接变量
2. 前端 `VITE_API_BASE_URL`
3. 数据源配置里的真实数据库权限

很多“页面空白”或“运行失败”其实不是 UI 问题，而是这三层中的某一层没有打通。
