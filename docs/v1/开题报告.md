# 开题报告

## 1 选题目的及研究意义

当前多数中小企业的业务数据分散存储于各类业务系统中，缺乏统一的数据语义抽象与低门槛分析工具，使得 IT 人员需频繁开发与维护查询语句，业务端则存在指标口径不一、复用困难、上线周期较长等现象。正如相关研究所述：“中小企业在数字化转型中存在成本过高、路径模糊、人才短缺等问题”[1]，数据层面的协作与维护成本也长期居高不下。本系统拟构建一套基于自研 DSL 的查询引擎，通过拖拽式交互自动生成 DSL，后端将 DSL 转换为参数化 SQL，避免手写 SQL，并在源头上控制安全与模板复用。这种 DSL 方式能够在保持表达力的同时限制自由度，使查询意图具备可校验、可审计、可复用的特性。

为减少跨团队沟通成本，系统将提供数据集管理模块，包含字段别名、字段类型、基础聚合及表关联关系，统一业务口径并降低建模门槛，从而缓解数据口径分裂和重复定义的问题。考虑到目标用户常处于内网或合规要求严苛的环境，系统选择可私有化部署的轻量形态，降低资源占用与运维复杂度，以便快速落地并兼顾安全性与成本控制。

在易用性上，系统计划引入 AI 辅助能力作为扩展功能，通过调用生成式 AI 服务接口（如 OpenAI、文心一言等）将自然语言转换为领域特定语言（DSL）草案。基于程学旗等[2]提出的‘智能算法安全需构建动态审计机制，通过形式化验证与人工复核确保生成内容的合规性’这一核心观点，系统不直接执行生成结果，而是采用‘schema 校验+HITL（人在回路）’的安全审核机制：先通过 DSL 结构化模式（schema）校验草案的语法与结构合规性，再经人工确认（HITL）锁定最终内容，形成‘生成-校验-确认’的闭环，确保辅助功能的可控性与合规性[2]。这一辅助策略既降低业务人员的学习成本，又避免生成式结果直接作用于数据源带来的安全风险。如后续排期充足，可进一步探索基于 AI 的图表推荐功能及 AI 生成商业风格 PPT 功能，但核心功能不依赖 AI 能力。

与市面上现有产品相比，本系统具有以下差异化特点：一是提供完整的管理界面，不仅可以作为看板软件直接使用，还支持导出图表 key，用户可在其他页面中通过开放组件库嵌入这些看板，实现一次编辑、多处复用；二是提供 AI 辅助能力作为扩展功能，通过自然语言交互即可搭建看板，降低使用门槛；三是采用自研的 metric-engine 包实现 DSL 解析与 SQL 生成，采用 monorepo 架构管理多个包，体现出良好的架构思维与包拆分设计。综上，本课题旨在在可实现的工程边界内，为企业提供"DSL 查询引擎 + 数据集管理 + 可视化看板 + AI 辅助（扩展）"的完整链路原型，以验证轻量可视化查询在私有化场景的可行性与价值。

## 2 国内外研究现状

### 2.1 国内研究现状

国内在数据查询语义化、可视化分析领域的研究起步较早，且伴随商务智能（BI）、自助式数据分析技术的发展逐步深化，形成了学术理论探索与工程化产品落地双线并行的发展格局，研究重心从早期面向传统商务智能的语义层查询实现，逐步向轻量化、语义驱动、自然语言交互与嵌入式可视化方向演进。
在早期研究阶段，国内学者聚焦商务智能语义层的可视化查询软件设计，解决传统 BI 系统中业务人员查询门槛高、语义复用性差的问题。李康年 [3] 针对传统商务智能应用的语义层查询缺陷，设计并实现了面向商务智能语义层的可视化查询软件，通过细粒度划分语义查询组件、完全面向对象的语义对象建模，实现了语义查询到 SQL 的自底向上转换，同时支持外部数据分析功能扩展与多 BI 系统语义层适配。该研究首次将语义层抽象与可视化查询结合，解决了业务人员无需编写 SQL 即可完成数据查询的核心需求，奠定了国内 BI 领域语义查询的技术基础。但受限于当时的技术架构，该研究仅适配传统商务智能系统，采用本地部署模式，存在架构偏重、语义模型配置复杂、不支持轻量化私有化部署等问题，无法适配中小团队的灵活使用场景。
随着自然语言处理与深度学习技术的发展，国内研究转向语义驱动的自然语言查询与智能可视化方向，重点突破自然语言转 SQL（NL2SQL）与图表智能推荐的技术瓶颈。杨梦琴 [4] 针对关系型数据库自然语言查询难、可视化适配性差的问题，提出语义驱动的数据查询与智能可视化模型，基于 LSTM 神经网络与 Word2Vec 词嵌入技术构建 NL2SQL 模型，通过 SQL 依赖关系图解决了传统 Seq2Seq 模型的查询条件顺序问题，同时结合表格透镜与表代数实现高维数据的智能可视化推荐，将自然语言查询的 SQL 生成准确率提升 15%。该研究实现了自然语言交互与可视化的深度融合，大幅降低了数据查询的操作门槛。但该研究偏向学术实验，仅支持单表查询与简单 SQL 生成，未考虑企业级场景的语义口径统一、跨表关联建模需求，且未形成可私有化部署、可嵌入式复用的工程化方案，难以直接落地于企业实际业务系统。
在工程化产品与应用层面，国内已涌现出多款成熟的数据分析与可视化工具，形成了覆盖企业级与中小团队的产品体系，但在轻量化与语义建模结合层面仍存在明显短板。面向大型企业的产品侧重语义治理与全功能覆盖，语义建模能力完善，但架构厚重、私有化部署与定制化成本高；面向中小团队的开源产品上手门槛低、功能轻量化，但语义层建模能力薄弱，缺乏统一的指标口径管理与跨表关联设计，同时嵌入式集成能力不足，无法与企业现有业务系统深度融合。整体来看，国内现有产品尚未形成兼顾轻量语义建模、可视化查询、嵌入式复用与私有化部署的一体化解决方案，与中小团队低成本、灵活化、可嵌入的数据分析需求存在 mismatch。
综上，国内相关研究与产品已完成从传统 BI 语义查询到自然语言驱动可视化查询的技术迭代，早期研究奠定了语义层与可视化结合的理论基础，中期研究突破了自然语言转 SQL 与智能可视化的技术瓶颈，现有产品则覆盖了不同规模企业的基础数据分析需求。但现有研究仍存在明显缺口：早期研究技术架构老旧、轻量化不足，中期学术研究缺乏工程化落地能力，现有产品则在轻量语义建模、嵌入式能力与私有化部署的平衡上存在短板。针对这一缺口，开展轻量语义建模的可视化查询系统研究，整合轻量化语义抽象、拖拽式可视化查询、AI 辅助自然语言交互与嵌入式可视化能力，既贴合国内企业数字化的实际需求，也填补了当前研究与产品的技术空白，具备重要的研究价值与实践意义。

### 2.2 国外研究现状

国外在语义建模、商业智能可视化查询领域的研究起步早、体系成熟，历经形式化语义规范、智能交互可视化、专用语义层架构三个阶段的迭代发展，形成了理论研究与工业落地深度融合的技术体系，为本课题的轻量语义建模与可视化查询系统研发提供了核心参考。
在商业智能的语义形式化描述研究方向，国外学者率先针对自然语言需求歧义性、数据语义不统一的痛点，提出受控自然语言（CNL）用于 BI 系统的语义规范定义。Rodrigues 等 [6] 研发了 CNL-BI 与 ITLingo ASL 两类受控自然语言，构建了覆盖多维数据模型、OLAP 操作、交互式可视化图表的完整语言范式，可精准描述医疗 BI 场景中的维度、事实、用例与 UI 交互组件，解决了传统需求描述难以机器解析、业务语义模糊的问题。该研究确立了语义建模的核心逻辑：将底层物理数据映射为业务可理解的逻辑视图，通过约束语法与词汇消除歧义，为轻量语义层的字段抽象、表间关联定义、指标口径统一提供了标准化理论依据。同期，基于数据仓库的 OLAP 语义建模研究持续深化，星型、雪花模型成为语义组织的基础范式，推动语义层从单纯的数据映射向业务语义封装升级，为可视化查询系统奠定了底层数据逻辑基础。
在大模型驱动的交互式可视化查询领域，以大语言模型（LLM）为核心的智能交互技术彻底重构了传统可视化分析的人机交互模式。Aodeng 等 [7] 提出的 InReAcTable 框架，针对表格数据可视化故事构建中洞察碎片化、用户认知负担重的核心问题，创新性融合结构过滤与语义推理双模块：通过子空间图缩小数据搜索范围，结合检索增强生成（RAG）与思维链（CoT）提示策略，实现与用户分析意图对齐的动态洞察推荐，支撑迭代式可视化数据故事构建。该研究突破了传统可视化查询依赖固定规则的局限，验证了 “轻量语义抽象 + 大模型语义理解” 在降低用户使用门槛、提升探索式分析效率上的核心价值，为本课题 AI 辅助可视化查询模块的设计提供了直接技术参考。此外，VizGPT、LIDA 等国外研究成果进一步实现了自然语言到可视化图表的自动转换，完善了智能可视化查询的技术链路。
在专用语义层架构设计与落地方向，国外学界明确了语义层在数据架构中的核心地位，为轻量语义建模提供了架构支撑。Suhra [5] 系统梳理了语义层从 BI 工具内嵌到 ** 专用语义层（DSL）** 的演进历程，指出传统 BI 工具内置语义层会形成数据孤岛，而独立部署的专用语义层可实现跨平台指标复用、业务逻辑统一、查询性能优化，提出了包含数据建模、转换、存储、API 访问的专用语义层完整架构，并结合 Uber 的 uMetric 实践验证了其在企业级场景的落地价值。该研究明确了轻量语义层的核心设计原则：解耦物理数据与业务视图、轻量化部署、可复用指标管理，为本课题轻量语义建模体系的设计提供了架构指导。
从商业化产品落地来看，国外已形成成熟的可视化查询产品矩阵，隐式印证了上述研究的实践价值：早期 Tableau、Power BI 等工具将语义层封装在产品内部，虽易用但存在语义孤岛；后续 Looker 通过 LookML、QuickSight 依托专用语义层实现了跨工具语义统一；Metabase、Mode 等轻量化产品则聚焦中小团队，集成轻量语义建模与拖拽式可视化查询能力，同时开放嵌入式 SDK 适配业务系统集成需求。这类产品既遵循了专用语义层的架构规范与受控自然语言的语义建模方法，又吸收了大模型驱动的智能交互理念，成为当前国外主流的数据分析解决方案。
整体而言，国外研究已构建起完整的技术体系，但仍存在适配性短板：一是传统语义建模方案依赖专业人员配置，轻量化、低门槛特性不足；二是大模型驱动的可视化分析多聚焦公有云场景，私有化部署能力薄弱；三是商业化产品在自定义语义口径、可控化 SQL 生成、嵌入式深度集成等层面难以兼顾灵活性与轻量化。上述研究成果为本课题提供了理论与技术支撑，而现有研究与产品的不足，也明确了本课题聚焦轻量语义建模、私有化部署、嵌入式可视化查询的创新方向。

## 3 相关技术原理及技术路线

### 3.1 技术原理

#### 3.1.1 自研 metric-engine DSL 引擎

本系统采用自研的 metric-engine 包实现 DSL 解析与 SQL 生成，这是本系统的核心技术组件。metric-engine 使用 knex.js 作为底层数据库访问层，理论上支持 knex 支持的所有数据库类型，当前以 MySQL 为主要适配对象。

metric-engine 的核心设计思想借鉴基于对象的特定域语言（DSL）构造方法[8]中 DSL 语义定义与解释分离、领域语义与通用语义解耦的核心原理，将查询意图（DSL）与具体执行方言解耦；通过统一的 DSL 描述语言定义查询逻辑，再由引擎转换为目标数据库的参数化 SQL，实现 DSL 层与执行层的独立演进与灵活适配。DSL 采用 JSON 结构描述维度、指标、过滤、排序、分组、分页与数据源元信息，前端拖拽生成的查询意图可被 metric-engine 直接校验与转换，形成可审计的统一描述。

metric-engine 的核心能力包括：

- **DSL 解析与校验**：解析 DSL 结构，验证字段存在性、类型匹配、权限范围等；
- **多数据库 SQL 生成**：基于 knex 生成适配目标数据库的参数化 SQL 语句，支持 SELECT、WHERE、GROUP BY、ORDER BY、LIMIT 等基础操作；
- **指标系统**：支持多种聚合函数（COUNT、SUM、AVG、MAX、MIN、DISTINCT_COUNT），支持表达式指标、行列级指标、同环比计算等高级功能；
- **连接管理**：提供数据库连接池管理，确保连接正确关闭，避免连接泄漏。

通过 metric-engine 的分层设计，将 DSL 与具体数据源解耦，从而保持不同数据库在使用体验上的一致性。这一架构设计体现了良好的工程实践，将核心查询能力抽取为独立包，便于复用和维护，同时为未来扩展更多数据源类型奠定了基础。

#### 3.1.2 数据集与语义层管理

数据集模块负责管理和处理数据模型，是连接数据源与查询的桥梁。语义层采用轻量设计，聚焦维度指标核心抽象，仅提供字段别名、数据类型、基础聚合规则及一跳表关系，不做多跳关联推断或复杂数据血缘追踪。这一设计贴合语义层“把复杂技术细节转化为易懂业务术语”的核心目的，同时通过精简功能控制工程复杂度，保障可视化拖拽查询功能的可交付性。

数据集模块的核心功能包括：

- **字段管理**：管理数据集中的字段信息，包括业务别名（中文名称）、技术名称（库表字段名）、数据类型（数值、日期、字符串等）；
- **聚合与用法约束**：定义允许的聚合方式（求和、计数、平均等）以及是否可作为维度或指标使用；
- **表关系管理**：支持手动配置表之间的关联关系，系统分阶段支持表关联能力。初期仅支持单表查询；中期支持可配置的三表直接 join（用户手动配置关联关系，系统支持最多三个表的关联查询）；
- **指标管理**：支持定义和管理数据指标，包括基础聚合指标、表达式指标等。

通过数据集模块的管理，前端在拖拽式交互中可以根据语义层配置实时生成查询 DSL，并在生成后立即触发 Schema 合法性与必填/枚举校验，从而在源头过滤掉字段缺失、类型不匹配或越权访问等问题。

#### 3.1.3 AI 辅助与安全闭环

AI 辅助模块是本系统的扩展功能，在完成前端基础功能后优先实现。该模块通过调用现成的 AI API（如 OpenAI、文心一言、通义千问等，支持配置为内网可访问的 API 或本地模型服务），将用户输入的自然语言转换为 DSL 草案。所有 AI 生成的结果需经过 DSL 校验、权限过滤与人工确认后才能执行，以确保可控性并降低误用风险。

AI 辅助模块采用 LangChain/LangGraph 框架实现，工作流程如下：

1. **自然语言理解**：接收用户的自然语言查询请求；
2. **DSL 草案生成**：调用 AI API 生成符合系统 DSL 规范的查询草案；
3. **Schema 校验**：对生成的 DSL 进行 JSON Schema 校验，检查字段存在性、类型匹配等；
4. **权限过滤**：检查用户是否有权访问目标数据集和字段；
5. **用户确认**：将校验通过的 DSL 草案呈现给用户，用户可以查看、编辑并确认；
6. **执行与结果返回**：用户确认后，DSL 提交执行，返回查询结果。

安全与审计机制贯穿执行链路：

- **DSL 隔离**：SQL 注入的核心成因是数据和控制结构使用同一传输通道[9]，本系统采用 DSL 作为轻量语义中间层，天然实现用户输入与 SQL 执行的隔离，用户不直接接触底层 SQL，可有效防范 SQL 注入攻击。
- **参数化查询**：metric-engine 全程使用参数化 SQL，避免注入风险；
- **白名单函数**：限制可使用的函数，防止危险操作；
- **限流与缓存**：如时间允许，为执行查询接口添加限流和缓存机制，防止资源滥用；
- **审计日志**：记录用户 ID、操作时间、数据集、查询内容概要等信息，满足合规审计需求。

如后续排期充足，可进一步探索基于 AI 的图表推荐功能，以及 AI 生成商业风格 PPT 功能，但核心功能不依赖 AI 能力。

#### 3.1.4 系统架构

本系统采用 monorepo 架构管理多个包，主要包括：

- **server**：NestJS 后端服务，提供 RESTful API，包括数据源管理、数据集管理、查询执行等功能；
- **metric-engine**：自研 DSL 解析与 SQL 生成引擎，是本系统的核心库；
- **ui-react**：基于 React 的前端 UI 组件库，采用类似 shadcn 的设计风格；
- **ui-core**：前端核心逻辑库。

这种 monorepo 架构体现了良好的包拆分设计思想，将不同职责的代码分离到独立包中，便于维护、测试和复用。同时，通过 pnpm workspace 管理多个包，可以统一版本控制和依赖管理。

## 4 研究难点及目前存在的问题

### 4.1 研究难点

#### 4.1.1 DSL 引擎设计与实现

用于商务智能（BI）可视化查询系统的领域特定语言（DSL）设计，需兼顾表达力与简洁性。正如火山引擎 DataWind 的设计理念所示[10]，代码语言曾成为业务人员实现个性化分析的屏障，而优秀的 BI 查询语言需通过简洁的交互方式，让无代码背景的人员也能实现灵活的个性化分析，同时避免过度复杂的设计增加系统实现成本。metric-engine 的 DSL 设计需要在满足查询需求的同时，保持足够的简洁性。过于复杂的 DSL 会显著提升解析器的实现难度，超出本科毕业设计的工作量范畴；但如果设计过于简化，又可能无法满足基础查询需求，因此需要在两者之间找到适宜的平衡点。

#### 4.1.2 AI 辅助的可控性与安全性

AI 辅助系统不应直接执行自动生成的查询逻辑，而应将其视为待验证的草案，通过校验机制与用户确认环节确保操作的安全性与可控性。若将 AI 生成的 DSL 草案不经审查直接执行，可能引入字段引用错误、不合理的聚合逻辑，甚至触发越权数据访问，进而导致查询失败或敏感信息泄露。因此，在保持 AI 辅助便捷性的同时，必须在系统层面构建包含语法校验、权限检查与人工确认的多重保障机制。

### 4.2 目前存在的问题

#### 4.2.1 语义层复杂度控制

当语义层的设计超出基础字段别名定义和简单聚合功能时，引入复杂的数据血缘追踪和多表关联逻辑，会明显提高系统的开发难度和失败风险。本毕设将聚焦语义层的基础功能（字段别名、简单聚合），避免自动推断多表复杂关联、构建完整指标血缘等 heavy 需求 —— 这一选择既能控制开发复杂度，匹配本科毕设的时间周期，也能满足“拖拽查询可视化”的核心功能诉求。

#### 4.2.2 私有化部署的权限与审计

私有化部署场景下，权限与审计方案不用设计得太复杂，只要能覆盖基础安全需求（比如防范注入攻击、记录关键操作），同时让用户用着方便就行 。企业内网对数据安全要求较高，需要有权限控制和操作记录的机制，但如果设计得太繁琐（比如细化到每行每列的权限、复杂的角色继承规则），不仅不好实现，还会让用户用着麻烦。怎么在满足基本安全需求的同时，做出简单好用的权限与审计方案，是本课题要解决的问题。

### 4.3 拟采取的措施

#### 4.3.1 DSL 设计平衡

JSON Schema 作为一种具备明确语义的声明性结构描述语言，可精准界定查询 DSL 中的必填/可选字段、数据类型及枚举约束，通过限定实例结构的合法表达范围，有效压缩非预期表达空间，进而提升 DSL 的语法可控性与验证有效性。通过 JSON Schema 严格约束 DSL 的结构，只保留与业务直接相关的查询要素（维度、指标、过滤、排序、分组、分页），不引入复杂的子查询、窗口函数或 SQL 方言特性，从而将 DSL 的复杂度控制在可管理范围内。

#### 4.3.2 AI 辅助的可控闭环

现有研究指出，通过人在回路的过程化交互实现 AI 推理透明化与可控修正，是提升 AI 辅助可靠性的关键路径 [11]。系统遵循 "面向过程的 AI 辅助" 原则，将 AI 输出严格限定为可编辑的草案，关键字段与聚合逻辑均需显式标注其语义来源，并经用户主动确认后方可执行。。具体流程包括：

1. **草案生成**：AI 生成的 DSL 草案以"草稿"状态呈现，用户可以在界面上查看和编辑；
2. **校验验证**：系统对草案进行 JSON Schema 校验、字段存在性检查与权限验证；
3. **用户确认**：通过校验后仍需用户点击确认按钮才能执行；
4. **风险提示**：对于检测到的高风险操作（如全表扫描、大范围聚合），系统会在界面上显示提示信息，要求用户二次确认，从而确保 AI 辅助能力不会直接控制数据访问。

#### 4.3.3 轻量级权限与审计方案

- **全链路安全校验机制**：采用前后端双重数据校验模式，MySQL 数据库操作全程使用参数化 SQL 语句规避注入风险，兼顾自助分析灵活性与数据安全性
- **权限控制**：采用简单的用户-数据集映射表，记录每个用户可访问的数据集列表，在查询执行前进行权限校验；
- **审计日志**：记录用户标识、操作时间、数据集、查询摘要等基本信息，支持按用户、按数据集、按时间范围等维度进行基础查询，满足合规审计需求。

# 文献总结

在企业日常运营中，数据分析越来越重要。但很多业务人员面对数据库、SQL、报表工具时，常常“无从下手”：不懂技术、不会写代码、看不懂字段名。而 IT 或数据团队又忙于处理各种取数需求，效率低、响应慢。为了解决这个问题，近年来出现了“语义层”和“可视化查询”这类技术，目标是让普通人也能轻松查数据、看报表。

## 语义层：让数据“说人话”

所谓“语义层”，简单来说，就是把数据库里的“技术语言”翻译成“业务语言”。比如，把字段 user_id 叫做“用户编号”，把 order_status = 1 解释为“已支付”，这样业务人员就能看懂、能用了。
最早的研究就意识到这个问题。李康年（2009）在做商务智能系统时，提出用“对象化”的方式封装数据表和字段，做成“语义对象”，让前端可以拖拽使用。比如，把“订单表”包装成一个“订单”对象，里面包含“订单编号”“下单时间”“金额”等可读字段。这样，业务人员不需要懂数据库结构，也能完成基本查询。
后来，胡圣明等（2006）进一步提出，可以用“特定领域语言（DSL）”的方式来建模。他们把业务逻辑拆成“视图对象”和“模型对象”，视图对象面向业务人员，模型对象负责底层数据逻辑。这种分离让系统更容易维护，也更容易扩展。比如，换一个数据库，只要改模型对象，视图对象不用动。
到了现在，语义层不再只是某个报表工具的附属功能，而逐渐变成一个独立的、企业级的数据逻辑层。Ramla Suhra（2024）提出“专用语义层（Dedicated Semantic Layer）”的概念，强调它应该统一管理指标、维度、计算逻辑，避免各部门“各搞一套”，导致数据不一致。
这些研究说明：一个好的语义层，不是简单地改个名字，而是要建立一套清晰、可复用、可管理的业务语义体系。但问题也来了——很多系统建模过程太重，需要专业人员花几周甚至几个月去设计，维护成本高，反而成了负担。
所以，本课题强调“轻量语义建模”：不追求一次性建完所有模型，而是按需构建，快速迭代。比如，先建一个“销售报表”用的语义模型，后面再逐步扩展。这样更适合资源有限的中小企业。

## 可视化查询：从“拖拽”到“对话”

有了语义层，怎么让用户方便地查数据？最常见的就是“可视化查询”——通过图形界面，点一点、拖一拖，就能生成报表。
Pedro das Neves Rodrigues 等（2023）研究了如何用可视化语言（如 CNL-BI、ASL）来表达复杂的分析操作，比如钻取、切片、聚合。他们的方法能让用户在不写代码的情况下，完成多维分析。但这类工具通常还是需要用户理解一定的分析逻辑，对新手来说仍有门槛。
于是，自然语言查询开始兴起。火山引擎 VeDI（2023）推出的“DataWind-分析助手”，允许用户直接用中文提问，比如“上个月华东区销售额是多少？”，系统就能自动生成图表。这背后是大语言模型（LLM）在起作用，它能理解自然语言，并转换成数据查询逻辑。
这听起来很智能，但也有问题。Kaviraj Pather 等（2025）指出，大模型的推理过程像“黑箱”，它怎么得出这个结果的，用户不知道。有时还会“幻觉”——编造数据或逻辑。比如，你问“去年利润增长了多少”，它可能随便编个数字出来。
为了解决这个问题，他们提出了 Vis-CoT 框架，把模型的推理过程“画”出来，变成一个可视化的思维链。用户可以看到系统是根据哪些数据、做了哪些计算，得出这个结论的。如果发现哪一步错了，可以手动修改。这就像老师批改作业，不仅告诉你答案，还展示解题步骤。
这个思路很有启发性：可视化查询，不只是“展示结果”，更应该是“展示过程”。特别是在企业场景中，数据决策关系重大，不能只靠“AI 一句话”，还得让人能看懂、能验证。
所以，我认为理想的可视化查询系统，应该是“自然语言输入 + 可视化逻辑展示 + 人工可干预”的结合。用户可以轻松提问，系统给出初步结果，同时展示背后的查询逻辑，用户可以检查、调整，最后确认输出。这样既高效，又可靠。

## 系统实现与落地：安全、轻便、能用

再好的设计，最后都要落地。一个系统能不能用，不仅看功能，还要看是否安全、是否好部署、是否适合企业现状。
首先，安全是底线。叶良艳（2018）专门研究了 SQL 注入问题——攻击者通过在输入框里写恶意代码，窃取数据库数据。虽然我们用语义层屏蔽了直接写 SQL，但如果系统在后台拼接 SQL 语句，仍然可能被攻击。解决办法是用“参数化查询”、严格校验输入，或者加防火墙。这些技术不炫酷，但必不可少。
其次，智能系统本身也要安全。程学旗等（2025）提出“智能算法安全”的概念，强调算法要有“可信、可管、可控”的能力。比如，系统生成的分析结论，不能是“拍脑袋”来的，要有依据；管理员要能监控、能干预；系统要能自我检测异常。这对大模型驱动的查询系统尤其重要。
最后，系统得“接地气”，能真正用起来。王柏村等（2023）研究发现，中小企业数字化转型最大的问题是：缺钱、缺人、缺方向。他们不可能像大企业那样，花几百万建数据中台、请一堆数据工程师。
所以，他们更需要“轻量级”的解决方案：部署快、成本低、上手简单。而“轻量语义建模”正好符合这个需求。它不需要推倒重来，可以在现有数据库上加一层语义封装，快速支持几个核心报表，之后再慢慢扩展。这比“大而全”的系统更现实。
从技术实现上，胡圣明等（2006）提出的“视图对象（VO）和模型对象（MO）分离”思路也很实用。我们可以把业务人员看到的字段、指标做成“视图对象”，把连接数据库、写 SQL 的逻辑做成“模型对象”。两者通过配置关联，这样换数据库或改字段，只改模型部分就行，不影响前端使用。
这种设计不仅灵活，也方便维护。对于中小企业来说，这种“小步快跑”的方式，比“一步到位”更可行。

## 总结与思考

总的来说，目前关于语义层和可视化查询的研究已经打下了一定的理论和技术基础：语义层从对象封装发展到专用语义层，目的是提高数据的易理解性和统一性；交互方式从拖拽式操作进化到自然语言查询，不断降低使用难度；在系统安全与实施方面，也更加重视数据安全、算法可信度以及中小企业的适应性。然而，仍有一些问题存在：语义建模过程通常太复杂，需要专业人员长期投入，难以适应快速变化的业务需求；自然语言查询虽然方便，但缺乏透明度，难以获得用户的完全信任；大部分系统还是主要针对大企业设计，对中小企业的友好度不足。因此，本课题希望构建一个更轻量、透明且实用的可视化查询系统：简化建模过程，按需构建以降低使用门槛；可视化查询逻辑，支持人工检查与修正；注重安全防护，适应中小企业的现状，实现快速部署使用。我期望这个系统不仅能展示 AI 技术，更能真正为业务人员节省时间、提高效率。即使它并不完美，只要能解决实际问题，就很有价值。
