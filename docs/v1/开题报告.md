# 开题报告

## 1 选题目的及研究意义

在多数中小企业的数据分析场景中，业务数据主要沉淀在 MySQL 数据库中，缺乏统一的语义抽象与低门槛分析工具，导致 IT 需反复编写或改造 SQL，业务侧则面对口径不一致、复用困难、上线周期长等问题，协作成本与维护成本长期居高。本系统拟构建一套基于自研 DSL 的查询引擎，通过拖拽式交互自动生成 DSL，后端将 DSL 转换为参数化 SQL，避免手写 SQL，并在源头上控制安全与模板复用。这种 DSL 方式能够在保持表达力的同时限制自由度，使查询意图具备可校验、可审计、可复用的特性。

为减少跨团队沟通成本，系统将提供数据集管理模块，包含字段别名、字段类型、基础聚合及表关联关系，统一业务口径并降低建模门槛，从而缓解数据口径分裂和重复定义的问题。考虑到目标用户常处于内网或合规要求严苛的环境，系统选择可私有化部署的轻量形态，降低资源占用与运维复杂度，以便快速落地并兼顾安全性与成本控制。

在易用性上，系统计划引入 AI 辅助能力作为扩展功能，通过调用现成的 AI API（如 OpenAI、文心一言、通义千问等）将自然语言转换为 DSL 草案，但不直接执行生成结果，需经 DSL 校验与人工确认，以确保可控性与合规性。这一辅助策略既降低业务人员的学习成本，又避免生成式结果直接作用于数据源带来的安全风险。如后续排期充足，可进一步探索基于 AI 的图表推荐功能及 AI 生成商业风格 PPT 功能，但核心功能不依赖 AI 能力。

与市面上现有产品相比，本系统具有以下差异化特点：一是提供完整的管理界面，不仅可以作为看板软件直接使用，还支持导出图表 key，用户可在其他页面中通过开放组件库嵌入这些看板，实现一次编辑、多处复用；二是提供 AI 辅助能力作为扩展功能，通过自然语言交互即可搭建看板，降低使用门槛；三是采用自研的 metric-engine 包实现 DSL 解析与 SQL 生成，采用 monorepo 架构管理多个包，体现出良好的架构思维与包拆分设计。综上，本课题旨在在可实现的工程边界内，为企业提供"DSL 查询引擎 + 数据集管理 + 可视化看板 + AI 辅助（扩展）"的完整链路原型，以验证轻量可视化查询在私有化场景的可行性与价值。

## 2 国内外研究现状

### 2.1 国内研究现状

国内自助 BI 与低代码分析工具在中小企业与行业私有化场景近年快速普及，典型做法是以拖拽式界面和 SQL 模板降低使用门槛，但大多仍强依赖手写 SQL 或半自动生成，导致业务人员需要 IT 支持才能完成复杂查询，语义口径仍然分散。现有产品为了兼顾上线周期与成本，往往在语义层设计上采用极度轻量化策略，仅提供字段别名、简单聚合和少量预置指标，缺少对字段类型、数据质量与关系约束的标准化描述，结果是跨团队共享数据时仍然需要额外的口径对齐成本。另一方面，企业数据中台普遍引入基于 JSON 的查询描述或领域特定语言（DSL）以解耦前后端，借助模板化与参数化方式控制安全与复用，但多数实现针对内部服务调用，缺少面向业务用户的可视化建模与校验界面，从而在易用性与可控性之间存在落差。

在关系型数据库场景方面，以 MySQL/ClickHouse/HTAP 数据库为核心的实时或准实时分析，国内现有低代码可视化 BI 工具的自助查询功能多通过 SQL 解析或模板注入技术实现，但现有方案在复杂场景下仍存在显著局限 —— 面对宽表处理、多表关联等实际业务需求时，常因语义理解偏差、查询逻辑不完整导致错误率较高，进而使得参数校验、数据类型自动映射、跨源聚合查询及多用户权限隔离等核心功能仍需依赖大量后端定制开发来保障可用性。

语义层方面，国内不少实践在数据中台阶段提供"轻语义 + 补丁式口径"的模式，即对核心指标给出别名与聚合口径，再通过文档或 Wiki 说明额外限制，但缺少结构化的 Schema 约束，导致前端 DSL 生成时难以做强校验，也难以自动选择合理的图表或排序方式。简化语义层固然降低了构建成本，但也导致口径漂移与二义性问题，尤其在多表关联、多业务线共享数据集时更为突出。当前也有团队探索用 JSON Schema 或类似规范描述维度、指标与关系，但多停留在后端配置层，没有前端可视化建模与即时校验的配套流程。

在可视化与交互层，国内多数轻量 BI 产品提供基础图表（柱/线/饼/表格）和看板拼装，部分支持自动图表推荐，但常依赖字段类型启发式或固定模板，缺少与数据分布、聚合语义结合的智能推荐；同时，对导出、权限与审计的支持往往简单，难以满足合规要求的私有化场景。国内私有化部署 BI 的研究与应用中，性能优化与资源轻量化已成为核心研究方向。企业内网环境对 BI 服务的易运维性、低资源占用提出刚性需求，尤其是行业型企业在数字化转型中，亟需适配本地 IT 架构的轻量化分析方案。然而当前主流 BI 工具为保障跨场景通用性，普遍集成了厚重的 SQL 解析引擎、多源数据兼容组件及冗余功能模块，导致部署门槛升高、服务器资源消耗过大，且后续升级维护需专业技术团队支撑，与企业追求的轻量化部署、低成本运维目标形成突出矛盾。

在开放组件库方面，国内尚未看到成熟的面向 BI 场景的嵌入组件库方案。大多数 BI 产品以 SaaS 形式提供服务，或以整体解决方案交付，缺乏像 shadcn 那样可按需引入的组件化嵌入能力。这一差异化方向为本课题的产品设计提供了创新空间。

AI 辅助方向上，国内已有产品尝试 NL→SQL 或 NL→ 可视化草稿，但在企业私有化落地时面临两个问题：一是安全校验不足，生成的查询缺少强校验与安全隔离，容易引入高风险操作；二是部署限制，模型通常依赖外部大模型或云端推理，难以满足数据出域和内网部署要求。因此，更可行的路径是 NL→DSL 草案，再由严格的 Schema 校验、权限过滤与人工确认，既提升易用性，又保留可控性。

在 AI 生成 PPT 方面，据笔者了解，已有大厂团队调研过 AI 生成营销风格 PPT 的实现方案，但目前尚未看到成熟的商业化产品落地。这一方向如能实现，将为数据分析产品带来显著的差异化价值，是值得探索的亮点功能。

### 2.2 国外研究现状

在国外商业智能与数据可视化领域，主流平台普遍采用中间 DSL/AST 或逻辑计划来描述查询意图，再生成参数化 SQL 或分布式计算计划，以实现跨数据源适配与安全控制，这类做法强调将用户意图与具体方言解耦，减少注入风险并提升复用性。早期系统多聚焦关系型数据库，如采用模板化 SQL 配合参数绑定；近年随着云数仓与多源异构的兴起，更多产品在 DSL 中加入数据源元信息、类型约束与优化提示，再由后端调度执行并统一结果格式。

在可视化推荐与交互分析方面，国外研究强调“数据分布 + 字段语义 + 任务意图”三要素联动。典型工作会先对表格列进行类型推断与统计特征提取，再结合用户的分析任务（比较、趋势、分布、相关性等）生成候选图表，并提供可编辑的视图规范（如 Vega-Lite）。这类方法通常将字段角色（维度/度量）、唯一值数量、缺失值比例、聚合方式与排序等信息编码到推荐模型中，以生成默认图表或推荐备选图表，从而降低用户的配置成本。一些研究进一步探索交互式“意图捕获”，通过用户的拖拽、筛选与鼠标行为来推断其分析目标，再动态更新推荐结果。

在语义层与元数据管理上，国外大型 BI / 数据平台强调 "逻辑模型" 或 "语义模型" 以统一指标口径。常见实践是将维度、指标、时间范围、过滤条件与安全规则写入模型文件或元数据服务，然后由前端查询构建器或 DSL 生成器读取并约束用户的选择范围，减少指标歧义与重复定义。和国内方案相比，国外部分 BI 工具的语义模型会包含更细致的权限控制和数据追踪功能，但这样的模型配置复杂、部署麻烦；而轻量化的设计思路正逐渐普及，通过简化字段映射和基础聚合功能，就能支持简单的可视化需求，很适合小团队、快速迭代的使用场景。

AI 与自然语言接口方面，国外不少产品与研究原型支持 NL→SQL、NL→DSL 或 NL→ 可视化规范，但普遍将安全与可控性放在首位。主要做法包括：一是中间语义生成，让模型生成中间语义（如 DSL/逻辑计划），再经严格 Schema 校验与权限过滤后才提交执行；二是解释确认流程，提供"解释—确认"流程，要求用户在界面上核对字段、过滤条件、聚合方式与数据源，再点击执行。这种"模型生成草案 + 人工确认 + 参数化执行"的闭环，是当前国际上较为可行的企业级落地路径，既利用了模型的易用性，也控制了误用与越权风险。

在产品形态上，国外轻量化 BI / 可视化工具常采用前后端分离的单页应用（SPA）架构，搭配轻量的 RESTful 接口实现数据交互，便于灵活部署；部分工具还配备了低代码的看板编辑器，支持通过可视化操作完成图表布局、数据关联的配置。部署方面，SaaS 模式与自托管模式并行，针对医疗、金融等行业的合规需求，自托管版本会保留参数化查询、审计日志、行列级权限及密钥管理接口，确保数据使用“可控 + 可追溯”。

综合国外研究与产品趋势，可以看到几项共性：

1. **DSL/语义层抽象**：广泛使用中间 DSL/语义层抽象，将用户意图与执行方言解耦，强化参数化与安全；

2. **可视化推荐**：重视可视化推荐的可解释性与默认合理性，用统计特征与任务意图驱动初始图表，并允许用户细粒度调整；

3. **AI/NL 能力定位**：AI/NL 能力被视为"辅助"而非"直接执行者"，必须经过 Schema 校验、权限约束与用户确认；

4. **轻量架构**：在异构数据与私有化部署场景下，更倾向于轻量可移植的架构，同时保留审计、权限与限流等企业级控制点。

这些做法对本课题的启示是：需要以 DSL 为中心串联语义、校验与执行；在可视化推荐与 NL 辅助上坚持"草案 + 校验 + 确认"的闭环；提供一致的结果格式与安全审计；并以轻量部署形态降低私有化成本。

## 3 相关技术原理及技术路线

### 3.1 技术原理

#### 3.1.1 自研 metric-engine DSL 引擎

本系统采用自研的 metric-engine 包实现 DSL 解析与 SQL 生成，这是本系统的核心技术组件。metric-engine 使用 knex.js 作为底层数据库访问层，理论上支持 knex 支持的所有数据库类型，当前以 MySQL 为主要适配对象。

metric-engine 的核心设计思想是将查询意图（DSL）与具体执行方言解耦，通过统一的 DSL 描述语言定义查询逻辑，再由引擎转换为目标数据库的参数化 SQL。DSL 采用 JSON 结构描述维度、指标、过滤、排序、分组、分页与数据源元信息，前端拖拽生成的查询意图可被 metric-engine 直接校验与转换，形成可审计的统一描述。

metric-engine 的核心能力包括：

- **DSL 解析与校验**：解析 DSL 结构，验证字段存在性、类型匹配、权限范围等；
- **多数据库 SQL 生成**：基于 knex 生成适配目标数据库的参数化 SQL 语句，支持 SELECT、WHERE、GROUP BY、ORDER BY、LIMIT 等基础操作；
- **指标系统**：支持多种聚合函数（COUNT、SUM、AVG、MAX、MIN、DISTINCT_COUNT），支持表达式指标、行列级指标、同环比计算等高级功能；
- **连接管理**：提供数据库连接池管理，确保连接正确关闭，避免连接泄漏。

通过 metric-engine 的分层设计，将 DSL 与具体数据源解耦，从而保持不同数据库在使用体验上的一致性。这一架构设计体现了良好的工程实践，将核心查询能力抽取为独立包，便于复用和维护，同时为未来扩展更多数据源类型奠定了基础。

#### 3.1.2 数据集与语义层管理

数据集模块负责管理和处理数据模型，是连接数据源与查询的桥梁。语义层采用轻量设计，聚焦维度指标核心抽象，仅提供字段别名、数据类型、基础聚合规则及一跳表关系，不做多跳关联推断或复杂数据血缘追踪。这一设计贴合语义层“把复杂技术细节转化为易懂业务术语”的核心目的，同时通过精简功能控制工程复杂度，保障可视化拖拽查询功能的可交付性。

数据集模块的核心功能包括：

- **字段管理**：管理数据集中的字段信息，包括业务别名（中文名称）、技术名称（库表字段名）、数据类型（数值、日期、字符串等）；
- **聚合与用法约束**：定义允许的聚合方式（求和、计数、平均等）以及是否可作为维度或指标使用；
- **表关系管理**：支持手动配置表之间的关联关系，系统分阶段支持表关联能力。初期仅支持单表查询；中期支持可配置的三表直接 join（用户手动配置关联关系，系统支持最多三个表的关联查询）；
- **指标管理**：支持定义和管理数据指标，包括基础聚合指标、表达式指标等。

通过数据集模块的管理，前端在拖拽式交互中可以根据语义层配置实时生成查询 DSL，并在生成后立即触发 Schema 合法性与必填/枚举校验，从而在源头过滤掉字段缺失、类型不匹配或越权访问等问题。

#### 3.1.3 AI 辅助与安全闭环

AI 辅助模块是本系统的扩展功能，在完成前端基础功能后优先实现。该模块通过调用现成的 AI API（如 OpenAI、文心一言、通义千问等，支持配置为内网可访问的 API 或本地模型服务），将用户输入的自然语言转换为 DSL 草案。所有 AI 生成的结果需经过 DSL 校验、权限过滤与人工确认后才能执行，以确保可控性并降低误用风险。

AI 辅助模块采用 LangChain/LangGraph 框架实现，工作流程如下：

1. **自然语言理解**：接收用户的自然语言查询请求；
2. **DSL 草案生成**：调用 AI API 生成符合系统 DSL 规范的查询草案；
3. **Schema 校验**：对生成的 DSL 进行 JSON Schema 校验，检查字段存在性、类型匹配等；
4. **权限过滤**：检查用户是否有权访问目标数据集和字段；
5. **用户确认**：将校验通过的 DSL 草案呈现给用户，用户可以查看、编辑并确认；
6. **执行与结果返回**：用户确认后，DSL 提交执行，返回查询结果。

安全与审计机制贯穿执行链路：

- **DSL 隔离**：DSL 作为中间层天然具备隔离能力，用户不直接接触 SQL，可以有效防止 SQL 注入攻击；
- **参数化查询**：metric-engine 全程使用参数化 SQL，避免注入风险；
- **白名单函数**：限制可使用的函数，防止危险操作；
- **限流与缓存**：如时间允许，为执行查询接口添加限流和缓存机制，防止资源滥用；
- **审计日志**：记录用户 ID、操作时间、数据集、查询内容概要等信息，满足合规审计需求。

如后续排期充足，可进一步探索基于 AI 的图表推荐功能，以及 AI 生成商业风格 PPT 功能，但核心功能不依赖 AI 能力。

#### 3.1.4 系统架构

本系统采用 monorepo 架构管理多个包，主要包括：

- **server**：NestJS 后端服务，提供 RESTful API，包括数据源管理、数据集管理、查询执行等功能；
- **metric-engine**：自研 DSL 解析与 SQL 生成引擎，是本系统的核心库；
- **ui-react**：基于 React 的前端 UI 组件库，采用类似 shadcn 的设计风格；
- **ui-core**：前端核心逻辑库。

这种 monorepo 架构体现了良好的包拆分设计思想，将不同职责的代码分离到独立包中，便于维护、测试和复用。同时，通过 pnpm workspace 管理多个包，可以统一版本控制和依赖管理。

### 3.2 技术路线

#### 3.2.1 后端核心模块开发

在技术路线的起始阶段，系统首先完成后端核心模块的开发工作：

1. **数据源模块**：实现 MySQL 数据源的配置、连接测试、元数据获取（表结构、列信息、外键关系）；
2. **数据集模块**：实现数据集的创建、字段管理、表管理、关联关系管理、指标管理；
3. **查询模块**：实现查询的定义、保存、执行功能，集成 metric-engine 完成 DSL 到 SQL 的转换。

#### 3.2.2 前端与组件库开发

在后端核心模块完成后，进入前端开发阶段：

**前端功能范围**：

1. **UI 组件库**：开发类似 shadcn 风格的 UI 组件，包括基础组件（按钮、输入框、表格等）和业务组件
2. **数据源管理界面**：实现数据源的配置、测试、查看、创建、编辑、删除等界面

## 4 研究难点及目前存在的问题

### 4.1 研究难点

#### 4.1.1 DSL 引擎设计与实现

用于商务智能（BI）应用的查询语言设计需兼顾表达力与简洁性，避免因覆盖过多功能特性而增加实现复杂度 。metric-engine 的 DSL 设计需要在满足查询需求的同时，保持足够的简洁性。过于复杂的 DSL 会显著提升解析器的实现难度，超出本科毕业设计的工作量范畴；但如果设计过于简化，又可能无法满足基础查询需求，因此需要在两者之间找到适宜的平衡点。

#### 4.1.2 AI 辅助的可控性与安全性

AI 辅助系统不应直接执行自动生成的查询逻辑，而应将其视为待验证的草案，通过校验机制与用户确认环节确保操作的安全性与可控性。若将 AI 生成的 DSL 草案不经审查直接执行，可能引入字段引用错误、不合理的聚合逻辑，甚至触发越权数据访问，进而导致查询失败或敏感信息泄露。因此，在保持 AI 辅助便捷性的同时，必须在系统层面构建包含语法校验、权限检查与人工确认的多重保障机制。

### 4.2 目前存在的问题

#### 4.2.1 语义层复杂度控制

当语义层的设计超出基础字段别名定义和简单聚合功能时，引入复杂的数据血缘追踪和多表关联逻辑，会明显提高系统的开发难度和失败风险。本毕设将聚焦语义层的基础功能（字段别名、简单聚合），避免自动推断多表复杂关联、构建完整指标血缘等 heavy 需求 —— 这一选择既能控制开发复杂度，匹配本科毕设的时间周期，也能满足“拖拽查询可视化”的核心功能诉求。

#### 4.2.2 私有化部署的权限与审计

私有化部署场景下，权限与审计方案不用设计得太复杂，只要能覆盖基础安全需求（比如防范注入攻击、记录关键操作），同时让用户用着方便就行 。企业内网对数据安全要求较高，需要有权限控制和操作记录的机制，但如果设计得太繁琐（比如细化到每行每列的权限、复杂的角色继承规则），不仅不好实现，还会让用户用着麻烦。怎么在满足基本安全需求的同时，做出简单好用的权限与审计方案，是本课题要解决的问题。

### 4.3 拟采取的措施

#### 4.3.1 DSL 设计平衡

JSON Schema 作为一种具备明确语义的声明性结构描述语言，可精准界定查询 DSL 中的必填/可选字段、数据类型及枚举约束，通过限定实例结构的合法表达范围，有效压缩非预期表达空间，进而提升 DSL 的语法可控性与验证有效性。通过 JSON Schema 严格约束 DSL 的结构，只保留与业务直接相关的查询要素（维度、指标、过滤、排序、分组、分页），不引入复杂的子查询、窗口函数或 SQL 方言特性，从而将 DSL 的复杂度控制在可管理范围内。

#### 4.3.2 AI 辅助的可控闭环

系统遵循"面向过程的 AI 辅助"原则，将 AI 输出严格限定为可编辑的草案，关键字段与聚合逻辑均需显式标注其语义来源，并经用户主动确认后方可执行。具体流程包括：

1. **草案生成**：AI 生成的 DSL 草案以"草稿"状态呈现，用户可以在界面上查看和编辑；
2. **校验验证**：系统对草案进行 JSON Schema 校验、字段存在性检查与权限验证；
3. **用户确认**：通过校验后仍需用户点击确认按钮才能执行；
4. **风险提示**：对于检测到的高风险操作（如全表扫描、大范围聚合），系统会在界面上显示提示信息，要求用户二次确认，从而确保 AI 辅助能力不会直接控制数据访问。

#### 4.3.3 轻量级权限与审计方案

- **全链路安全校验机制**：采用前后端双重数据校验模式，MySQL 数据库操作全程使用参数化 SQL 语句规避注入风险，兼顾自助分析灵活性与数据安全性
- **权限控制**：采用简单的用户-数据集映射表，记录每个用户可访问的数据集列表，在查询执行前进行权限校验；
- **审计日志**：记录用户标识、操作时间、数据集、查询摘要等基本信息，支持按用户、按数据集、按时间范围等维度进行基础查询，满足合规审计需求。

# 文献总结

随着企业数字化转型的深入推进，中小企业在数据分析领域面临着数据源分散、IT 资源有限、业务人员分析能力不足等多重挑战。传统的 BI 工具虽然功能强大，但在私有化部署、轻量化运维、低门槛使用等方面难以满足中小企业的实际需求。基于这一背景，本研究聚焦于构建一套基于 DSL 的轻量化可视化查询系统，旨在通过统一的查询抽象、轻量化的语义层设计和自研的 metric-engine 引擎，实现高效的查询体验。通过对相关领域文献的系统梳理，可以发现该研究方向涉及查询语言设计、语义层架构、AI 辅助能力、系统安全治理等多个技术领域的交叉融合。

## 中小企业自助 BI 的需求与挑战

在中小企业数据分析场景中，业务数据主要沉淀在 MySQL 数据库中，缺乏统一的语义抽象与低门槛分析工具，导致 IT 需反复编写或改造 SQL，业务侧则面对口径不一致、复用困难、上线周期长等问题。皮圣雷等人（2025）指出，国内面向中小企业的自助 BI 相关研究及产品实践，多聚焦于降低使用门槛、实现快速上线，却在数据可控性、语义统一性等方面设计不足，难以适配企业经营的动态需求。这一观察揭示了当前中小企业 BI 应用的核心矛盾：如何在降低使用门槛的同时，确保数据的可控性和语义的一致性。

李一平（2024）通过实际案例，进一步揭示了国内私有化部署 BI 的研究与应用中的核心矛盾：企业内网环境对 BI 服务的易运维性、低资源占用提出刚性需求，尤其是行业型企业在数字化转型中，亟需适配本地 IT 架构的轻量化分析方案。然而当前主流 BI 工具为保障跨场景通用性，普遍集成了厚重的 SQL 解析引擎、多源数据兼容组件及冗余功能模块，导致部署门槛升高、服务器资源消耗过大，且后续升级维护需专业技术团队支撑，与企业追求的轻量化部署、低成本运维目标形成突出矛盾。这一研究为本课题的轻量化架构设计提供了重要的实践指导，强调了在功能完整性与资源占用之间寻求平衡的必要性。

## 查询 DSL 的设计方法

面对上述挑战，设计一套既具备足够表达力又易于验证的查询描述语言（DSL）成为关键。Rodrigues 和 Silva（2023）系统性地探讨了用于商务智能应用的受控自然语言设计方法。该研究指出，用于 BI 应用的受控语言设计需兼顾表达力与简洁性，避免因覆盖过多功能特性而增加实现复杂度。研究者提出了一种基于受控自然语言的查询规范方法，通过限制语法范围和语义表达，在保持查询意图清晰表达的同时，有效降低了查询解析与验证的复杂度。该研究强调了参数化查询在安全性和可复用性方面的重要价值，为 DSL 设计提供了重要的理论指导。

在 DSL 的结构化描述与校验方面，Attouche 等人（2026）深入研究了现代 JSON Schema 验证中注释依赖的消除问题。该研究指出，JSON Schema 可精准界定查询 DSL 中的必填/可选字段、数据类型及枚举约束，通过限定实例结构的合法表达范围，有效压缩非预期表达空间，进而提升 DSL 的语法可控性与验证有效性。该研究提出了一种消除注释依赖的验证方法，使得 Schema 验证过程更加高效和可靠，这对于本课题中基于 JSON Schema 的 DSL 校验设计具有重要的参考价值，特别是在拖拽式交互的实时校验场景下，高效的验证算法能够显著提升用户体验。

然而，现有低代码可视化 BI 工具在自助查询功能实现上仍存在显著局限。Xiong 等人（2024）揭示，面对宽表处理、多表关联等实际业务需求时，常因语义理解偏差、查询逻辑不完整导致错误率较高，进而使得参数校验、数据类型自动映射、跨源聚合查询及多用户权限隔离等核心功能仍需依赖大量后端定制开发来保障可用性。这一观察为本课题的 DSL 设计指明了方向：需要在设计阶段就考虑参数校验、类型映射、权限隔离等安全与可用性需求，而非在实现阶段通过补丁式开发来解决。

## 语义层的轻量化设计

语义层作为连接业务术语与技术实现的桥梁，在统一业务口径、降低跨团队沟通成本方面发挥着关键作用。Suhra（2024）通过案例研究的方式，深入探讨了专用语义层架构的设计与实践。该研究强调，语义层采用轻量设计，聚焦维度指标核心抽象，仅提供字段别名、数据类型、基础聚合规则及一跳表关系，不做多跳关联推断或复杂数据血缘追踪。这一设计贴合语义层"把复杂技术细节转化为易懂业务术语"的核心目的，同时通过精简功能控制工程复杂度，保障可视化拖拽查询功能的可交付性。

Subha（2024）在另一篇同名研究中进一步指出，当语义层的设计超出基础字段别名定义和简单聚合功能时，引入复杂的数据血缘追踪和多表关联逻辑，会明显提高系统的开发难度和失败风险。和国内方案相比，国外部分 BI 工具的语义模型会包含更细致的权限控制和数据追踪功能，但这样的模型配置复杂、部署麻烦；而轻量化的设计思路正逐渐普及，通过简化字段映射和基础聚合功能，就能支持简单的可视化需求，很适合小团队、快速迭代的使用场景。这一研究为语义层的最小化设计提供了理论支撑，强调了在功能完整性与实现复杂度之间寻求平衡的重要性，为本课题的语义层设计提供了明确的指导原则。

## 系统架构与前端设计

在系统架构层面，现代 BI 系统普遍采用前后端分离的设计，单页应用（SPA）架构因其良好的用户体验和灵活的部署方式，在 BI 系统中得到了广泛应用。Anas 等人（2022）系统性地探讨了基于单页应用的 BI 仪表盘设计与实现。该研究指出，国外轻量化 BI/可视化工具常采用前后端分离的单页应用（SPA）架构，搭配轻量的 RESTful 接口实现数据交互，便于灵活部署；部分工具还配备了低代码的看板编辑器，支持通过可视化操作完成图表布局、数据关联的配置。该研究为 BI 系统的前端架构设计提供了实践参考，强调了 SPA 架构在提升用户体验和降低部署复杂度方面的优势，为本课题的系统架构设计提供了重要的技术选择依据。

在组件库设计方面，shadcn/ui 作为一种新兴的组件库模式，提供了可定制、可嵌入的 UI 组件方案。与传统组件库不同，shadcn 并不作为独立包发布，而是将源代码直接集成到项目中，便于深度定制和修改。本课题借鉴这一思路，计划开发类似 shadcn 风格的 UI 组件库，并提供嵌入能力，支持用户将看板组件嵌入到其他页面中使用，实现“一次编辑、多处复用”的产品形态。

## AI 辅助查询的实现

随着大语言模型技术的快速发展，AI 辅助的自然语言到查询转换（NL2Query）成为提升 BI 系统易用性的重要方向。然而，如何在利用 AI 能力提升易用性的同时，确保系统的安全性和可控性，是该领域面临的核心挑战。Zhang 和 Reicherts（2025）深入探讨了生成式 AI 在辅助人类决策中的应用与挑战。该研究强调，AI 辅助系统不应直接执行自动生成的查询逻辑，而应将其视为待验证的草案，通过校验机制与用户确认环节确保操作的安全性与可控性。系统应遵循"面向过程的 AI 辅助"原则，将 AI 输出严格限定为可编辑的草案，关键字段与聚合逻辑均需显式标注其语义来源，并经用户主动确认后方可执行。该研究为 AI 辅助查询构建的安全设计提供了重要的理论指导，强调了"草案+校验+确认"闭环的重要性。

在可视化推荐方面，Aodeng 等人（2025）提出了基于大语言模型的交互式可视化数据故事构建方法。该研究探讨了如何基于数据分布与字段类型进行图表推荐，通过分析表格数据的统计特征和字段语义，自动生成合适的可视化方案。该研究为 AI 辅助的图表推荐提供了技术思路，但其实现复杂度较高，对于轻量化系统而言，可能需要简化实现或作为可选功能。这一观察为本课题的 AI 辅助功能设计提供了参考：核心功能不依赖 AI 能力，AI 辅助作为核心功能开发，通过"草案+校验+确认"的安全闭环来保障可控性。

在 AI 生成 PPT 方面，据笔者了解，已有互联网大厂团队调研过 AI 生成营销风格 PPT 的实现方案，但目前尚未看到成熟的商业化产品落地。这一方向结合了数据分析与内容生成两大能力，如能实现将成为显著的差异化亮点。

## 安全与审计机制

在私有化部署场景下，BI 系统的安全性和审计能力是保障数据合规使用的重要基础。然而，如何在满足安全需求的同时，保持系统的易用性和轻量化，是该领域面临的重要挑战。Wang 和 Li（2024）针对金融服务业（BFSI）组织的自助分析治理问题进行了深入研究。该研究强调了在自助 BI 场景下，采用前后端双重数据校验模式的重要性：MySQL 数据库操作全程使用参数化 SQL 语句规避注入风险，同时依托模板化权限治理规则，兼顾自助分析灵活性与数据安全性。该研究为自助 BI 系统的安全设计提供了实践指导，但其治理方案相对复杂，对于资源受限的中小企业场景可能不够轻量。

Yellammala 等人（2025）提出了一种基于哈希码的查询转换技术，用于最小化 SQL 注入漏洞。该研究强调了参数化查询在防范 SQL 注入攻击方面的重要作用，指出私有化部署场景下，权限与审计方案不用设计得太复杂，只要能覆盖基础安全需求（比如防范注入攻击、记录关键操作），同时让用户用着方便就行。该研究为轻量级安全方案的设计提供了实践指导，强调了在安全性与易用性之间寻求平衡的重要性，为本课题的安全与审计设计提供了明确的指导原则。

## 研究总结

综合上述文献研究，可以看出，基于 DSL 的轻量化可视化查询系统设计涉及多个技术领域的交叉融合，需要在表达力与简洁性、功能完整性与实现复杂度、安全性与易用性之间寻求平衡。在 DSL 设计层面，需要兼顾表达力与简洁性，通过 JSON Schema 实现结构化校验，避免因覆盖过多功能特性而增加实现复杂度；在语义层设计层面，应采用轻量化的最小设计，聚焦核心功能（字段别名、数据类型、基础聚合），避免引入复杂的数据血缘追踪和多表关联逻辑；在 AI 辅助层面，应坚持"草案+校验+确认"的安全闭环，将 AI 输出严格限定为可编辑的草案，避免直接执行自动生成的查询逻辑；在系统架构层面，采用轻量化的 SPA 架构，便于私有化部署和灵活运维，同时采用 monorepo 架构管理多个包，体现出良好的架构思维；在安全审计层面，采用简单实用的方案，在满足基础安全需求（防范注入攻击、记录关键操作）的同时保持易用性。

这些研究成果为本课题的系统设计提供了重要的理论基础和实践指导，同时也指出了现有研究的不足和未来改进方向。例如，现有研究在 DSL 引擎设计、实时 Schema 校验、轻量化安全方案等方面提供了技术思路，但在如何将这些技术有机融合到一套完整的轻量化系统中，并结合产品化的嵌入组件库能力，仍需要结合具体应用场景进行深入探索。本课题正是在这一背景下，尝试构建一套"DSL 查询引擎 + 数据集管理 + 可视化看板 + AI 辅助 + 嵌入组件"的完整链路原型，以验证轻量可视化查询在私有化场景的可行性与价值。
